# Finish a proven empty financial market

A funded account can finish a broad tier-2 baseline search with zero properties, then spend later research turns checking narrower audiences in that same ZIP. In the inspected account, a baseline zero was followed by six later zero estimates. Their exclusion generations differed, so those historical requests are not treated as cache hits or retroactively skipped.

The prospective change uses the original baseline estimate immediately. After the existing tier-0 and tier-1 widening steps, the application calls `icash_finish_empty_financial_market` only for a tier-2 baseline on provider page one. Its service-only transaction requires:

- Current account/configuration/setup/market/policy and the existing Run, membership, funds, data-rights, filtering and exclusion-readiness checks.
- A direct, completed original estimate no more than five minutes old, evaluated with a post-lock clock. Shared estimates, active leases, missing fields, future receipts and changed query or exclusion generation fall back to ordinary per-arm discovery.
- An exact canonical property-only financial query, zero property totals, zero total results, zero page/people credits and an explicit final-page response.
- No operation on the current free request, no claimed page in the current account/revision and no unresolved discovery operation in any arm of that revision, including an orphan operation without a page row.
- Known current subset strategies and the exact reviewed SQL query-builder, readiness and market-finalization definitions. Baseline construction lives inside the pinned financial query validator; the merger preserves the conjunction of financial and experiment constraints. Unknown strategies or future dependency changes disable only this optimization.

The shared budget, account and configuration locks preserve the existing admission order. The exclusion generation and referenced experiment definitions remain locked during finalization. The function closes only the actual baseline page, exhausts the covered cursors without incrementing their page counters, and calls the unchanged inventory-rotation path. It does not invent a narrower-arm observation, quota request, billable work, seller result or successful new-market search.

The private immutable decision stores the exact original query, response, scope, policy, source timestamps and previous cursors. No customer identities or production receipts are included in the test fixtures. The decision table has RLS, no client/service table grants and a private immutable trigger; only the service-role RPC may make a decision through its guarded owner execution.

## Verification and release

The local regression first reproduces the old baseline-only completion retaining narrower cursors and the same empty ZIP. It then exercises successful market rotation, original evidence/money preservation, missing or stale proof, controls, mismatched source, all-arm unknown operations, replay, immutable records and no available authorized alternate market. The application regression covers missing additive schema and a lost success response; fallback to the original old-scope completion cannot finalize again.

Native PostgreSQL tests use a separate disposable localhost database and concurrent finalizers, late Pause/policy/exclusion/unknown-operation changes, source aging while waiting on a lock and rollback. They make no provider requests. These checks prove the transition mechanics, not a measured production speed improvement or future leads.

Install the additive migration only after its exact predecessor readback, independent review and canonical checks. Installation changes no existing function or customer row and starts no retrospective work. Deploy the matching application through the existing serialized release controller, then inspect naturally recorded decisions and successor-market work. Do not invoke the RPC on historical customer data to demonstrate it. A missing prerequisite keeps the PR held; do not claim the feature live from a merge or schema installation alone.

Application rollback stops new calls and restores normal arm-by-arm completion; keep the original decision records. No provider limit, pricing, mandatory financial filter, original uncertain purchase, customer control, contact authority or customer interface is changed.
