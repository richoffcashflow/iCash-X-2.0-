# Webinar entry speed

Public `/live/[webinarCode]` and `/webinar` entries now load a small entry component that starts the existing session request while the full room bundle downloads. The room consumes that same request, including its error, and retains the existing explicit retry action. Responses record their arrival time so waiting for the bundle does not shift the server clock. The existing loading layout is shared unchanged. A server-rendered preconnect hint warms the configured public storage origin without fetching or selecting a video before authorization.

New visitors save timezone, attribution, region and funding identity in their initial insert. Only a confirmed new visitor skips empty session history and the redundant metadata update. Only a newly generated funding token skips its purchase lookup; existing guest purchases and signed visitor resumes retain their checks. The exact newly created session skips empty personal chat history, while reused/concurrent sessions retain the bounded restore read. Settings load alongside visitor resolution. The normal anonymous first visit removes five database requests and two sequential network stages, retaining both rate-limit checks and every required access check.

No recording, session snapshot, offer, checkout deadline, playback position, measurement definition or autoplay policy changes. Video delivery already supports cached range requests and front-loaded MP4 metadata; this change targets entry setup. Existing viewers are not reloaded. No new database migration, provider configuration, worker release or paid test is needed.

Verification includes actual visitor and route bodies with isolated cookies/database fixtures: fresh and returning identities, an existing paid guest with a new visitor, signed resume with original payment evidence, concurrent session chat, access failure, shared pending/error results, clock preservation and manual retry. The built browser test holds the actual room chunk and proves session setup completes independently, with exactly one startup request after hydration and one additional request only after an explicit retry. Existing webinar autoplay, recovery, day/night, payment and reporting suites remain applicable. Local fixture results are not a production latency guarantee; measure production entry again after the ordinary reviewed release.
