# Independent-query timeout recovery

An admitted targeting search can time out after dispatch while its exact exclusion-list policy lives in `query_claims` and `research_list_id` remains null on the current discovery configuration. The older continuation only recognized unknown searches with a configuration-level list. The owning account therefore stayed on the unresolved operation even with funds and eligible markets; the separate bystander continuation deliberately does not handle an account's own unfinished purchases.

The correction recognizes supported `research-efficiency-v2` and `financial-prefilter-v1` policies with either saved `seller-targeting-v1` or `seller-filters-v1` plans through their immutable account, operation, revision, page, ZIP and policy evidence. Research v2 preserves its explicit nullable list; financial policies use the existing strict date/tier/list validator. Missing fields, unknown versions and malformed policies remain held. It does not need a retained estimate. A finished handler must be at least five minutes old, have exactly one admitted search, no result or cost receipt and no current discovery ticket. Existing membership, funding, Pause, automatic-work, rate, rights and geographic checks remain authoritative.

Under the existing budget lock, recovery snapshots the original configuration and moves only future work to an eligible different ZIP. It resolves all unresolved discovery scopes once before the bounded 64-market selection; a global unscoped unknown prevents continuation, and known unresolved ZIPs are excluded. Existing customer scope and feature controls are locked during selection. The original operation, reservation, request, query claim and money are unchanged. The original ZIP remains fenced, a stale worker cannot purchase against its former revision, and an exact late receipt remains bound to its original configuration without advancing the new cursor.

## Verification

`node tests/research-efficiency-database.test.mjs` exercises the actual continuation and late-result writer with synthetic data: staged-disabled behavior, missing or mismatched query evidence, pruned estimates, Pause, unfunded wallets, market restrictions, global unknown scopes, exactly-once recovery, unchanged spending and late-result idempotency. It covers targeting, baseline, explicit null-list and financial tier/date policies, with malformed-policy rejections. The pre-existing exclusion-list and completed-500 cases remain covered.

`python3 scripts/test-independent-search-continuation-postgres.py` uses only the disposable localhost PostgreSQL fixture. It tests concurrent Pause, settings, automatic-work, scope and global-unknown changes; twelve simultaneous recovery attempts; unchanged money; stale final admission; a locked late-receipt writer; and transactional migration rollback on predecessor drift. It is included in canonical Reliability checks.

## Rollout

Install `config/independent-query-stall-recovery.sql`, then `config/complete-query-stall-recovery.sql`, with their ordered migration receipts; the new setting defaults false. Both predecessor hashes and the existing financial-policy validator must match. Keep migration bytes and installed ledger versions aligned. After review and successful exact-head canonical checks, complete the normal automatic release and verify exact-main production deployment and worker readiness. Then enable `icash_research_private.settings.independent_query_continuation_enabled` under the operating-budget lock. The existing acquisition scheduler invokes continuation; do not replay the old request or issue a paid development probe.

Observe the private stalled-search snapshot and subsequent ordinary production receipts separately. A rotated configuration is recovery progress, not a completed search, outreach success or sale. Disable only the new setting to stop future continuation; do not reverse completed cursor changes or remove original snapshots/holds. The UI remains unchanged and must continue reporting a delay until actual work supports healthier status.
