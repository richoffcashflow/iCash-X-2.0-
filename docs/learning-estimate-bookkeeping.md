# Receipt-check bookkeeping and learning

An unchanged original-cost check updates `icash_operation_spend.estimate_checked_at`. The learning trigger previously treated that timestamp as new evidence, incrementing the account learning generation and workspace revision. Production read-only evidence on November 16 showed thousands of held checks in one hour; this is unnecessary work, not proof that those original financial holds can be cleared.

The forward migration adds that one column to the trigger's existing ignored fields only for `public.icash_operation_spend`. State, costs, settlement evidence, other fields, inserts, deletes and changes on other tables retain their previous behavior. A cursor change alongside new evidence still wakes learning. No billing, recovery cadence, provider request, customer-work status, UI or learning-policy change is included.

The migration takes the shared transaction advisory lock with a three-second lock timeout before reading the pinned predecessor. It validates private execution rights, compares the exact installed rewritten definition and every unchanged `pg_proc` metadata field after replacement, and preserves the function owner, SECURITY DEFINER, empty search path, volatility and ACL. No active function manifest refers to this trigger in the inspected source. A different source or privilege layout must be reviewed; the migration rejects replay and drift, including concurrent replay after waiting for the first installation. The release runner must own the outer transaction and schema-history write.

The predecessor `pg_get_functiondef` MD5 is `821d84ea09d109cfdd5b1272a0745509`; the verified rewritten definition is `39ca7becf8bd1b7a33e4babf58b9c0e0`.

Validation uses synthetic original-operation rows and the real predecessor trigger. PGlite covers cursor-only changes, simultaneous receipt/cost/state changes, unrelated fields/tables/schemas, discovery scheduling, inserts/deletes, newer-generation retention, rollback and source/ACL drift. Native PostgreSQL reproduces the old timestamp update timing out behind a learning-row lock, verifies the fixed poll completes, and proves concurrent real receipts and settlements still synchronize and increment the generation. Run `node tests/learning-estimate-bookkeeping.test.mjs` and `node scripts/test-learning-estimate-postgres.mjs` against the required disposable target. Normal exact-head/main CI and release verification remain required.

After release, verify the installed trigger hash, unchanged privileges and ordinary learning freshness. Compare useful settled work and receipt-check volume separately; this fix does not claim to resolve every pending original operation or prove zero stalled accounts. Rollback restores the exact predecessor trigger in a guarded forward migration; never reset learning generations, source rows or financial holds.
