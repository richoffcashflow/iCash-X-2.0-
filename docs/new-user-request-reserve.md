# New-user research request reserve

Ordinary research must leave capacity for users who fund their bot later in the
same shared request window. The initial policy protects 980 of the existing
9,800 requests, with up to 50 protected requests per eligible account during the
24 hours after its first verified live credit funding. Later refills do not
restart this eligibility. This is request capacity, not free customer credits.

Every admitted request still consumes the same organization-wide minute/day
counter. Regular work uses the unreserved capacity; protected requests consume
an immutable debit from the remaining reserve. Spending reserve capacity does
not create a second 980-request pool. Legacy and accountless request paths
cannot borrow the reserve. Provider retry holds and the absolute limits win.

Account eligibility retains membership, Run/Pause and available funded credits.
The reserve does not change data selection, provider purchase authority,
contact-hour rules, financial holds, actual-cost billing or manual controls.
Calls, texts and active deals keep their existing admission rules. Starting
research is not evidence of a seller reply, completed outreach or a deal.

Account identity is carried through scheduler checks, owner previews, exports,
original export recovery, exact requested-ZIP lookup and temporary-list cleanup.
If a starter already depends on an attached shared exclusion list, one exact
account/list/lease-bound synchronization may use its allowance. List creation,
unknown-list recovery and accountless maintenance cannot borrow this reserve.
The final limiter decides
atomically; a scheduling preview cannot itself spend a request. Original
request IDs remain one-use even when multiple workers contend.

The admin capacity view separates ordinary capacity from requests reserved for
new users. Total exhaustion, provider holds and ordinary-reserve boundaries
remain distinct. Monitoring never resets counters or creates usage.

## Release and rollback

The policy installs disabled. Before activation, run the exact release's
offline suites, native PostgreSQL contention scenarios, production build,
browser checks and dependency audit; verify the matching production web and
worker commits and installed database functions. Then enable the one private
policy row while retaining counters and all admission history. Disable that
row to stop future reserve allocation without erasing past consumption.

If the shared daily limit was already consumed, enabling a reserve cannot
restore requests retrospectively. The existing window must expire normally.
No paid provider demonstrations or historical-request replays are part of
verification. The first ordinary production starter outcome must be observed
separately before claiming its latency improved.
