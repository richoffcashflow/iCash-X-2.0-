# iCash X ad-to-work experience

## First visit

Ad → one above-the-fold start button with no typing or sign-in → plainly labeled fictional walkthrough using illustrative events → a small, server-enforced anonymous allowance for genuine bot work → real findings and remaining allowance in the same workspace → optional funding choice, proposed $20 first pack, daily limit, disclosures, and payment → expanded autonomous work after all platform preflight checks pass. The bot scans houses and land; do not ask the customer to choose a property type. Ask for legal contract identity only when needed to issue a real agreement. Infer a first market if reliable and ask one short confirmation only if ambiguous. No lead list, vendor API key, campaign, script, CRM, or prompt setup.

The free sandbox labels the conversation and all seller, agreement, buyer, and $20,000 gross spread outcomes as fictional. It teaches the process through the bot's work: rank, check contact permissions, qualify the seller, verify facts and signers, negotiate within limits, match a buyer, coordinate title, and close. The animated example uses illustrative events; it does not call providers. It is not a payout claim. Free live use is an actual, capped bot run through a server-issued anonymous session; allowed operations, lifetime and daily provider-cost ceilings, and quantity limits load from versioned server configuration only after vendor pricing and data rights are verified. It pauses at the limit, never silently converts to paid balance, and never sends calls or texts without channel authorization. Display only actual findings and expenditure. Collect only essential details; contract preference appears when a real contract is ready.

Keep the start button, walkthrough, free balance, real activity, and optional funding in one mobile workspace. There is one obvious action at a time and no global menu. Only a trusted server-side account snapshot can route a returning visitor into a needed decision, resumed work, or a low-credit funding step. A browser ad parameter cannot identify the user.

## Returning ad visitor

Capture attribution once, resolve the signed-in account server-side, and call `nextDestination`. Route to the real pending task first, then low-balance funding for active opportunities, resume if paused with sufficient credits, or the working activity view. Show the actual available balance, current work, and why more credits would be used. A returning click is never a purchase event. If the session is expired, preserve attribution and return to the intended next action after login.

## Useful reasons to return

Show truthful milestones: seller replied, owner/signers confirmed, offer reviewed, contract signed, buyer interested, title opened, deposit confirmed by escrow, closing scheduled, closed. Send a short notification only for a material event, user decision, deadline, or low-credit pause. Let users choose channels and quiet hours. Provide a concise daily summary rather than repeated empty pings. Suppress duplicate notifications.

## Optimization

Track ad click, content view, registration, first property analysis, funding, activation, meaningful seller conversation, qualified seller, contract, buyer, title, and close as separate events. Send Meta Purchase only for a settled credit payment with its true amount and event ID deduplication. Optimize on actual gross profit and downstream closed-deal cohorts as data matures, with holdouts for onboarding, pack, and message tests. Do not make the product spend credits merely to improve engagement or ad metrics.

The fictional free run is measured as `simulation_started` and `simulation_completed`, separate from `first_property_analyzed` and every real transaction milestone. Never send a simulated contract, buyer, closing, or gross spread as a Meta conversion. Funnel optimization should compare free-run completion, registration, first funded purchase, genuine automation activation, retained credit use, and actual gross profit by cohort. Store attribution only where permitted and join conversion events to verified account/payment records before server-side reporting.

## Failure paths

If payment succeeds but the worker is not ready, credit the ledger, keep the operation paused, explain the exact blocker, and provide a path to support/refund handling. If a provider fails mid-operation, release unused reservations, retry idempotently, preserve all legal deadlines, and notify only when the user must act. If an ad click cannot identify a returning user, show the standard entry path and recover their account securely; never use ad parameters as identity.

## One-page app entry

The opening page is the workspace: balance first, live activity directly below. A free example runs inside the activity card and is labeled fictional. Add Credits expands inline in the balance card. No type selection, chat input, campaign setup, external funding page, or plan grid. Credit explanations expand inline. Live free allowance remains unavailable until account, grant ledger, provider data and dispatch exist.

The primary acquisition conversion is a successfully settled credit purchase with accurate value and currency, verified server-side and deduplicated with the browser event. Add Credits clicks and demo completion are diagnostics, not purchases. This preview has no payment or Meta Purchase dispatch. Preserve pause, spending controls, and accessible disclosures in the same workspace.

## Activity motion

The video reference is translated into a running status, start/pause/resume control, and a newest-first animated log beneath a stable credit balance. The sample produces 14 explicitly fictional events with 1.6-second routine events and 2.8-second milestone pauses, pauses while the tab is hidden, stops at completion, and never changes customer funds. Its timeline is labeled compressed. `ActivityFeed` is shared presentation for demo or live events; live ingestion is not connected. Production must pass only persisted, authenticated, deduplicated events and real ledger balances. No artificial filler or accelerated live outcome claims.

## Faster preview and payment-first account claim

The sample now uses 1.6-second routine events with 2.8-second milestone pauses (about 24 seconds total). Its completion triggers `conversionOffer` in demo mode: a truthful free-preview-complete prompt, not fake depleted credits or a real pending deal. Live prompts require a trusted server snapshot, a true credit pause, and insufficient balance for the next charge. Unit tests reject unverified, invalid, sufficient-balance, and non-paused inputs. There is no conversion guarantee and no live analytics transport yet.

Planned checkout is embedded on the workspace with email collected as part of payment. Before payment, store an anonymous checkout claim bound to a secure HttpOnly session; do not require a password. A signed provider webhook must confirm paid status, amount, currency and the server price record, then atomically settle credits once against the checkout ID. A redirect or browser callback is never payment proof. Account claiming uses an expiring, single-use email link; do not email a generated password or log someone into an existing account just because checkout submitted its email. Only a verified existing session may attach credits directly to that account. Keep unclaimed purchases recoverable without duplicate grants. Optional password or passkey setup happens after claim. This is a design specification; payment, email, auth and database integrations are still absent.

## Conversations in the same workspace

Seller activity can expand to show conversation messages. The preview includes an explicitly fictional thread and disabled call/text controls. Production requires persisted transcripts/messages with access checks and retention controls. A user takeover must pause AI contact on that opportunity before enabling calls or sends; return control explicitly to the bot. Show a draft, recipient, channel and applicable charge before a manual send. Enforce opt-out, permission and contact hours for both manual and automated contact. On uncertain send/call status, reconcile the provider ID before retrying. Route an owner decision into one concise Needs You card above the feed, retaining the credit balance. Background 24/7 work belongs to the durable worker; it is not unrestricted around-the-clock calling.

Anonymous free work is research-only at launch: issue a finite server-side grant with atomic reservations, rate limits, expiration, and a platform-wide promotional cost ceiling. Browser storage cannot reset grants or authoritatively prove eligibility. The existing free gate now takes server-determined `sessionEligible` rather than requiring a signed-in account. Enable no anonymous work until the grant store and abuse controls exist. Claim and preserve eligible anonymous research after paid email verification without using the email string as authorization.
