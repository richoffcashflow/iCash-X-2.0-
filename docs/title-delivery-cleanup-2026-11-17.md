# Original title delivery recovery

The November 17 audit extends the response-cleanup repair to the original title opening email, ordinary title follow-up, and document/payment-preference update. After a rejected HTTP response, each dispatcher awaited cancellation of its response body before recording the existing delivery-review hold. A pending cancellation could therefore delay the durable original result and the independent buyer work that follows it.

Each path now initiates cleanup once, observes a later rejection, and immediately follows its existing failure path. This is one failure class in three additional closing paths. It adds no send retry, replacement email, successful-delivery receipt or title milestone. Existing exact snapshot/payload claims, request identities, current recipient and spending checks, 15-second request deadlines, and conditional state writes are unchanged. A newer canceled, dismissed or completed task remains in its newer state.

`tests/title-delivery-cleanup.test.mjs` uses native `Response`/`ReadableStream` failures with the actual service implementations. Its 23 offline scenarios cover pending/rejected/synchronously failing cleanup, a late rejection, blocked final claims, successful original receipts, no replay, newer task states, and actual journey processing continuing to an independent buyer message. On the unchanged predecessor, 11 pending-cleanup scenarios fail; these are test permutations of the same fault, not separate incidents. Provider sends and database boundaries are explicit isolated fixtures, so this does not prove a live email or closing.

The existing title request/update/follow-up, exact delivery snapshot, title-copy receipt, composed closing and funnel/journey suites remain required. There is no migration, policy activation, historical replay or paid test. Release through the existing reviewed exact-head/exact-main checks and serialized production verification; do not claim deployed recovery before that evidence exists.
