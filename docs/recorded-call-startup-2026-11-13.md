# Recorded outbound call startup

The owner's fresh November 12 evening demonstration reached the carrier but never started the AI. The original database evidence shows recording authorization followed by a terminal call, without a recording-start claim, recording SID, conversation, offer or contract. Preserve that attempt and its actual settlement. Resetting the account again does not repair this handoff.

Before dialing, the dispatcher also serialized caller-ID/routing verification and agent review. The final recording dispatcher repeated that sequence. Both stages now run the independent reviews together, retaining a fresh check at each boundary. Disabled numbers are rejected before provider reads, and no credit reservation, recording admission or dial can pass a pending or failed required review. The original intake-to-carrier-dial interval was about 41 seconds; the exact first-ring timestamp was not recorded.

The callback previously waited for canonical carrier readback and then fetched the reviewed agent and tools. Those independent reads consumed the same 12-second callback budget before recording authorization, recording startup and AI registration. They now run concurrently after signature, nonce, account and existing call binding validation. Every required result must still pass before final database admission. Agent/version/contract/stop checks remain fresh. Opt-outs do not wait for an agent review. Recording must be confirmed and saved before AI registration; no failed or uncertain operation is retried.

The real server/service regression uses a deterministic clock: 500ms database lookup, 6s carrier read and 5s agent review. The serial sequence reaches the 12s deadline at authorization; the concurrent sequence completes the entire handoff in 9 simulated seconds. Invalid identities/reviews, changed admission, opt-out, caller disconnect, provider failure and unknown recording start still stop the call. These synthetic timings are not measured live-call latency.

Entry failures now report a fixed phase, bounded elapsed time, fixed reason and typed HTTP status when available. They never log provider bodies, phone numbers, callback nonces or credentials. Previously the outer entry catch silently ended the call, making a timeout indistinguishable from other early failures.

The production build also performs a narrowly bound read-only inspection of the original failed owner call. It runs only on production main with a full commit SHA, expires November 15 UTC, and skips an existing immutable receipt. Canonical carrier identity, terminal age and callback nonce are checked before retaining HTTP status, bounded request duration, XML presence markers and notification codes in the private integration-check table. No provider write, dial, message, retry, financial change or contract action is available through that diagnostic. The extra receipt can identify whether the original carrier callback timed out; the preexisting silent logs alone do not prove the exact cause.

The owner also requested testing before another attempt. The demo contact step now performs an authenticated, owner-bound read-only setup inspection before enabling Start, with a manual recheck. It checks account/Run/credits, the current reviewed AI and offer tools, all configured call-capable demo lines, SMS lines/rates and reply configuration, and the standard one-seller purchase form and signing connection. Independent categories run concurrently with bounded reads; identical provider metadata GETs are deduplicated only within that inspection. Missing checks, errors and failed rechecks never count as passed. Navigation aborts the request and ignores late success. The inspection cannot create a lead, acquire a call permission, reserve money, dial, generate speech, send a text or create a contract. It is diagnostic, never a stored approval: normal final admission still repeats fresh checks. It does not establish a property's eligibility, a real ring, natural speech quality, a delivery receipt or a signature. The existing read-only outbound inspector now carries the active offer-policy revision into its structural guardrail and tool-schema checks.

Release requires exact-head Reliability checks and exact-main web/worker verification. There is no migration, provider-configuration change or retrospective outreach activation. The visible change is limited to the specifically requested setup check on the existing demo form. A successful release and offline tests do not prove a new live offer or contract delivery.
