# Webinar completion and shared chat

The November 11 audit found that the main webinar's final offer expired 13 seconds before the Day recording ended and 3 seconds before the Night recording ended. The completion route selected only unexpired offers, leaving these completed viewers without a destination. The shared chat feed also returned recent comments from the entire recording and the client relabeled them with the current viewer's position.

Completion now sends an eligible main viewer to the ordinary checkout for the same session when the configured or last reached ending offer was a checkout offer. It does not extend deadlines, reopen an expired in-player offer, substitute membership for an expired custom product, or redirect early completion/progress requests. Existing VIP, redirect-disabled, ownership and engaged-payment behavior is retained. Owner completion uses the isolated preview checkout, including expired Day/Night offers.

Shared chat requests include the viewer's bounded playback position. The database filters approved comments by recording position and excludes the viewer's own session before the 100-row limit. The original position survives polling and rewind hides future shared messages immediately, including an in-flight response. A viewer's own submissions retain their existing visibility. Recording, revision, preview, moderation, ownership and public-field restrictions remain unchanged. Old tabs that omit position use their saved progress checkpoint; messages with unknown positions are not replayed publicly.

Regression coverage exercises the actual completion route with the audited timings, saved deadlines and retries; active main/VIP checkout; owner preview; server filtering before pagination; original client timestamps, polling and rewind; session summaries and moderation isolation. These tests use fictional sessions and offline fixtures, with no customer messages or paid transactions.

The separate Meta audit found missing production `ICASH_META_ACCESS_TOKEN` and `ICASH_META_GRAPH_VERSION`, with queued server events that had never been attempted. This release does not invent credentials, change the configured pixel, replay events or claim delivery. Restoring CAPI requires an authorized token for that pixel, a supported Graph version and receipt-backed delivery verification. Browser Pixel and server tracking are separate.
