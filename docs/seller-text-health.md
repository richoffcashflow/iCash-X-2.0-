# Seller text protection and number monitoring

Approved November 1, 2026 after repeated cold introductions reached the same person through different property records and business numbers. A sender being enabled or a provider accepting an outgoing message does not verify incoming service.

Cold seller SMS now permits one introduction per recipient, across all account/property/number history. One unanswered reminder may follow 3–5 days after the original dispatch, on the same thread, only while existing contact evidence remains valid. After that window or a second attempted message, unanswered automated outreach pauses. Retired history, reserved sends and uncertain outcomes still count; changing property or number cannot reset the sequence. Existing requested-contact sequences, manually authored replies and source-backed negotiations retain their original admission rules. No consent, contact check, balance, provider receipt or eligibility date is renewed.

The scheduler checks the same guard before selecting new/recovery work. Final text admission checks it again under the existing budget and recipient locks, before reservation and at operation claim. The original account, sender, suppression, hours, funding, Pause and unknown-outcome gates still apply. Reply processing already precedes new introductions in the root scheduler and remains in that order.

New introductions name the actual saved buyer company (or principal), identify the exact street, ask the existing ownership question, and include `Reply STOP to opt out`. The message must fit the existing one-segment character policy; unsupported identities/addresses hold for review. The new `identity-v3` copy has its own assignment context and variant so it cannot inherit the old experiment's results. Existing assignments, sent copy and ownership/interest interpretation remain unchanged.

Natural stop-contact requests such as “Stop asking me” and a final “Stop.” suppress contact. Repeated refusals such as “I have told yall NO” pause automation. Quoted/negated speech, “stop by tomorrow” and price negotiations retain their existing interpretation. SQL, webhook normalization, text analysis and call results share the same tested source-word policy. Never infer carrier complaints from opt-out counts.

The owner-only admin overview refreshes each line's original receipts: today's property texts and customer updates, 24-hour property acceptance/delivery/review counts, incoming people, confirmed selling interest, opt-outs, refusals, complaint wording, carrier blocking notices and last saved non-carrier incoming message. Duplicate inbox/property representations count once. Carrier complaint totals remain explicitly unavailable. A missing incoming message is unverified service, not a confirmed outage; a saved message is an observation, not a guarantee of full carrier health. The dashboard never probes by sending a paid text.

720 remains enabled under the owner's resume instruction. 424 remains paused; this release cannot restore its carrier reputation and never moves its established conversations to another number.

Validation: offline PostgreSQL scenarios exercise duplicate properties/accounts/numbers, original dispatch timing, the reminder window, serialized final claims, uncertain sends, natural refusals, manual suppression, requested-contact exceptions, actual opener queue/copy parity and owner-only receipt monitoring. SQL/TypeScript refusal fixtures cover incoming normalization, text analysis and source-bound call results. Run `node --experimental-strip-types tests/seller-text-health.test.mjs` and the ordinary repository release checks. No paid development traffic.

Deployment: apply `20261101212803_seller_text_health.sql` once, verify the live functions/permissions and sender flags, then release the matching API/UI through the existing production pipeline. The database guards are compatible with the previous API. An API rollback should leave these protective database guards installed; do not clear historical controls or replay queued/uncertain messages to roll back copy.
