# Eighty-percent voice capacity

On November 5, 2026 the owner requested running at 80% of the upgraded Business plan's forty simultaneous calls. The approved ceiling is **32 total calls: 30 outgoing and two reserved for incoming**. The existing 1,000 daily outgoing conversation limit, incoming configuration, subscription, burst setting, prompts, tools and per-account admission remain unchanged. This is available capacity, not a promise of 32 occupied slots when eligible funded work is unavailable.

The previous application and database ceilings were twenty, and the outgoing agent was eighteen. Fresh subscription and exact reviewed-agent metadata bound the new 32/30 limits; a lower provider plan or observed agent limit still wins. Unknown subscriptions fail verification, stale observations retain the one-slot fallback, and unknown credit evidence cannot clear exhaustion.

The migration compares all five deployed function definitions with captured hashes, then changes only the three twenty-slot ceiling expressions. It leaves the optimized snapshot, recipient and uncertain-operation holds, per-account one-to-three-call limits, shared admission locks, and existing Pro approval receipts intact. Incoming arrivals do not subtract their reserve twice. The existing one-second voice issuance schedule and worker handlers already launch asynchronous calls; raising handler count is unnecessary for this concurrency change.

The separate provider change installs **disabled**. After the exact main commit passes canonical Reliability checks and both Vercel and Railway are confirmed on that commit, enable it with the service-only `icash_eighty_percent_voice_capacity_change('enable')` RPC. Ordinary production maintenance then validates the exact reviewed agent, branch and version, fresh available subscription credits, previous 18/1,000 limits, and matching main-branch limits. Only the winning durable claim may send one minimal main-branch PATCH from eighteen to thirty. It verifies the complete reviewed branch configuration after the change before recording completion. Daily allowance stays 1,000.

A timeout or lost receipt permits only an exact readback, never a second PATCH. Unknown outcomes remain held, and later ordinary capacity observations or manual reductions cannot reset the claim. Provider configuration failures remain independent of ordinary capacity refresh and maintenance. Final activation requires fresh saved observations of 32 total, thirty outgoing, two incoming and an applied receipt; no paid test calls are used.

Offline coverage exercises real deployed SQL, thirty outgoing plus two incoming in either arrival order, recipient collisions, unknown-operation quarantines and late provider identities, stale observations, credits, and prior receipt preservation. Native PostgreSQL contention tests require exactly one winner among twenty-four simultaneous claims and preserve that receipt across competing observations. Provider fixtures exercise lost writes/readbacks, reviewed configuration drift, insufficient plans, duplicate maintenance requests and disabled activation.
