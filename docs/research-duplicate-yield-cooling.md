# Reduce pulls from consistently duplicate inventory

The earlier supply rule cools an audience only after three completely duplicate pages. Three pages returning 24 repeated properties and one new property each therefore receive ordinary allocation indefinitely. On November 7, 2026 the owner requested another DealMachine efficiency review after substantial Scale-plan use.

The existing service-only supply reader now cools a ZIP/audience after each of its latest three original attempts returns at least 80% duplicates. Each receipt must reconcile new plus duplicate properties to its returned count, match the original account, exact static query and page size, have complete settled costs, and be no more than 24 hours old. A newer productive, pending, unknown, mismatched or incomplete attempt breaks the streak. Counts are compared as integers, without percentage rounding.

This is temporary allocation feedback. The existing one-in-five probe, all-cooled fallback and sole-available-audience fallback remain unchanged. Exact-page reuse, final purchase admission, account ownership, customer controls, financial eligibility and original receipts remain authoritative. This does not transfer customer contacts, change prices or quotas, revive a held purchase, or retire a market permanently.

## Verification and rollout

The focused PostgreSQL fixture reproduces the old allocation gap and covers the threshold boundary, productive recovery, pending/unknown costs, account/query/page-size mismatches, malformed totals, age/future timestamps, small pages, probes, fallback and ACLs. The migration checks the exact predecessor hash and preserves the function's metadata and existing bounded index scan. It changes a read-only selection predicate; it adds no locks, tables, writes or network calls.

Run canonical exact-head Reliability checks before production installation. Install only this reviewed migration, read back its exact function and service-only grants, then complete the normal automatic release. No application API or worker protocol changes are required. Existing application and worker releases can use the new predicate immediately. Historical migrations and financial/provider records must not be replayed.

Compare future new eligible properties, duplicate proportions, reported data credits, completed outreach and source-backed outcomes across equivalent demand windows. Record counts and request savings are not verified dollar savings or deal lift. DealMachine's monthly data credits and daily API requests are separate limits; duplicates may have zero new credit cost while still consuming requests. The later financial screen can still reject newly purchased data. This change does not claim to solve that separate yield issue.

Rollback restores only the original `icash_market_duplicate_supply(text,text,integer,jsonb)` definition from `config/research-market-duplicate-cooling.sql`, preserving its current private ACL and all original data. Do not reset cursors, reservations, quotas or purchases.
