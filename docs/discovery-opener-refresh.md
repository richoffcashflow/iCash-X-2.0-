# Source-bound discovery opener refresh

## Status

This is an initially disabled, operator-only implementation. Local synthetic
verification is separate from canonical CI, installation and activation. This
document is not evidence of a completed refresh or a delivered text. Investigated
drafts remain held until current evidence and every ordinary admission check
succeed. No development provider requests or texts are permitted.

## Why the ordinary recovery cannot clear this hold

A ready draft can outlive both its financial screening and its national DNC
observation. The existing opener recovery deliberately refuses stale evidence.
Its bounded scan is queue fairness, not permission to extend evidence dates.
Seller-intake research refresh requires a specific consented seller request;
reminder contact refresh requires an already delivered introduction. Neither
entrypoint may be widened to cover an unsent discovery introduction.

The new workflow must preserve the original account, property, owner-contact
source, phone, sending principal, sender, thread, message, tickets, purchases
and unknown financial outcomes. It is a distinct, initially disabled workflow.
Any historical candidate requires a private source-bound review rather than a
bulk age-based replay.

## Evidence and authority

The minimum recovery acquires one fresh exact-property response and one fresh
exact-phone national DNC response. Each provider stage requires its own durable
one-use claim, quota admission and current cost admission. A missing response
is an unknown purchase, not permission to retry or release money. Only identical
receipt persistence and processing of already saved responses may be retried.

Fresh property data must match the original property ID and pass the ordinary
financial-screening implementation. The previous screening must be archived
immutably before applying genuinely new receipt-derived values to the working
screening. Replacing its date without new data is forbidden.

The original paid owner result stays unchanged. Existing operational policy
already distinguishes immutable owner/phone ancestry from the freshness of a
national DNC observation. Reusing that ancestry is not new proof of ownership,
phone ownership or consent. A national observation is not state-list clearance.
All existing source quality, identity, consent, suppression and contact controls
remain authoritative.

A successor contact requires a separately reviewed discovery provenance branch;
inserting a recent receipt alone does not pass final admission. Application must
be atomic, recheck current controls and never send. Normal opener issuance and
dispatch retain all their existing checks, hours, budget and provider limits.
Applying eligible evidence can make the existing draft available to that normal
scheduler; it must not be used as a read-only diagnostic or a development test.
Any new Pause, STOP, manual takeover, source drift, sender change, dispatched or
uncertain work must keep the draft held.

## Provider contract

Official documentation checked November 16, 2026:

- [Address enrichment](https://api.docs.dealmachine.com/api-reference/enrichment/enrich-by-address)
  supports one exact address with `contact_audience: "none"`. This excludes
  people credits; matched property data costs at most one property credit.
  Responses echo the input and identify the matched property. Rewritten or
  mismatched addresses are not accepted as authority for another property.
- [Phone DNC](https://api.docs.dealmachine.com/api-reference/phones/check-dnc)
  returns national DNC status, not person enrichment. Missing `do_not_call`
  means exact-phone metadata may be unavailable and cannot clear the hold.
- [Credits](https://api.docs.dealmachine.com/concepts/credits)
  distinguishes actual newly charged `used` credits from evaluated and
  deduplicated records. A previous purchase is never assumed to make a request
  free. Settlement must use the original saved response and pricing snapshot.

## Required verification and release gates

Before registration for normal automatic release:

1. Review the complete inactive implementation, source-pinned predecessor chain,
   migration atomicity and all private function/table grants.
2. Exercise actual receipt, financial and contact SQL using synthetic fixtures.
   Cover malformed evidence, wrong account/property/phone, changed original
   source, missing costs, expired rights and every no-replay boundary.
3. Run native PostgreSQL contention and rollback tests, including competing
   claims, concurrent receipt writes/application and late Pause/STOP.
4. Run relevant existing opener, reminder-refresh, research and billing suites,
   type checks and canonical exact-head Reliability checks.
5. Use the existing release controller, not a parallel release. Verify the exact
   main web/worker source and installed migration before separate activation.
6. Record private, current candidate review and current rates/source rights.
   Verify the established sender's current health without a test message.
   Activation must remain bounded and must not silently include the historical
   backlog. Unknown original provider outcomes are never recovery candidates.

Rollback stops new acquisition/application, while preserving immutable receipts
and actual-cost reconciliation. It does not reverse charges, delete purchases,
reset consumed requests, re-enable senders or replay messages. Offline success
is not production throughput or delivery evidence.

## Operator sequence

The explicit worker is `scripts/discovery-opener-refresh.mjs`. It is not imported
by a route, scheduler, build or test hook. Its command-line guards require the
exact clean release checkout, an already enabled matching private release
policy, one reviewed renewal ID and an explicit provider-work flag. `--help` is
read-only; the real worker is production work, not a verification command.

After inactive installation and exact-release verification, the operator first
activates the private release policy with its immutable review reference. Each
draft is then separately inspected through the original-source snapshot and
staged using its exact expected hash. A single worker invocation can acquire at
most one provider stage. Later invocations may process saved receipts, but never
repeat an admitted request. The global one-request-per-minute pace and unknown
cost barrier apply even across different renewals.

When both actual costs and new evidence are valid, the workflow prepares a
successor for review. An exact final review and its short-lived application are
separate operator actions. They do not reset old tickets or create a new draft.
Never loop the worker to force past a hold, clear an unknown request, relax the
source hash or call apply merely to see whether it works.

## Local verification scope

- The billing suite uses real reservation, claim, ledger and settlement SQL with
  explicit source/quota fixture seams. It covers actual 3x/VIP pricing,
  provider-reported deduplication, malformed or unknown costs, one-use claims,
  post-quota expiry and atomic rollback. A real worker/property-qualification
  journey binds input echo, property ID, raw response and request-start time.
- The source/application suite uses current source-pinned DNC and final SMS
  guards. Its 20 scenarios cover immutable originals, exact review, concurrent
  control changes' sequential equivalents and the ordinary unchanged issuer.
  New receipts are synthetic and separately settled in this suite, not live
  purchases or proof of production provider behavior.
- Native PostgreSQL 17.11 verifies the same source/application guards with
  separate connections, observed competing preparation locks, late Pause/STOP,
  competing application, irreversible STOP revocation and ordinary ticket
  issuance after commit. It creates no SMS spend operation or provider ID.
- Worker/CLI checks cover request uncertainty, identical receipt-write recovery,
  raw-error persistence and exact clean-release/inactive-backend refusal.
- Migration checks prove the exact source mirror and outer-runner rollback of
  schema and ledger on source drift or a later failure. Installation is inactive
  and creates no provider requests.

These tests do not prove provider delivery, live cost invoices, complete native
financial-wrapper behavior or eligibility of an arbitrary historical draft.
The current bounded version excludes any associated recording, voice job,
other deal thread, signing envelope or unresolved handoff. Such records need
separate source-specific review rather than weakening these exclusions.
