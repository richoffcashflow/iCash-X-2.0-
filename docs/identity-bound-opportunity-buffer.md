# Pending work after a sending-identity change

The November 3 read-only audit found an account with available credits and 29 pending properties against its 25-property pipeline limit. Nineteen had settled owner-contact results whose exact operational records belonged only to the previous sending identity. The customer had changed their saved identity after those records were created. Dispatch correctly held 21 distinct calls before contacting anyone; it did not repeatedly redial a held job. The pipeline projection nevertheless treated the old-identity records as available outreach and blocked independent research.

`identity-bound-opportunity-buffer.sql` adds one exclusion to the existing stable, invoker-only pending-count function. It applies only when the original exact owner operation is settled with a settlement timestamp; the result matches the property; a nonblank current identity and exact old-principal source hash exist; and there is neither an operational record for the current identity nor a nonrevoked, unexpired legacy permission. An unknown purchase on the same property retains the buffer slot. Missing preparation, missing identity and ambiguous provenance remain counted.

The read-only counterfactual reduced this account's count from 29 to 10 while retaining all seven unknown owner purchases and three held preflights. This is a fixed diagnostic observation, not a claim that new research ran. Organization quota and the unchanged account, source, rate, credit and final-admission controls can still block work.

The migration changes only the pending-work projection. It does not rewrite identities or contacts, renew permission, clear money holds, change operations, issue outreach or re-enrich the old properties. Their original purchase and thirty-day owner-result guards still exclude them from new enrichment. The ordinary scheduler may select independent research only after all existing admission gates pass.

The PGlite regression loads captured production definitions and the existing current scheduler/source fixtures. It reproduces the filled buffer, tests the narrow exclusion and both alternative contact paths, preserves queued work and same-property uncertainty, checks source/account mismatch and missing settlement, restores the original count when the exact identity returns, and exercises Pause, membership, funds, quota and data-rights gates. Full before/after evidence remains identical, and the real scheduler issues only a discovery ticket inside a rolled-back offline test. The function's original ACL, volatility and security mode remain unchanged. No lock order changes or provider tests are involved.

Install only after checking the exact function hash and normal release validation. Verify ordinary production work separately. Reverting the projection must restore the captured prior definition; historical evidence does not need repair or removal.
