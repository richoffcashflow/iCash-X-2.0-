# Business calling readiness diagnostics

A saved seller call failed the business-number preflight twice although its stored outbound, forwarding and caller-ID fields were enabled. Its one permitted configuration recovery had already run; it still had no operation, recording, carrier call or AI conversation. The saved warning logs did not identify which live provider read failed. Those observations do not prove a provider outage, revoked number or safe second recovery.

Additional-number calling now reports a fixed check stage for readiness failures: stored readiness, provider configuration, active lease, caller ID, forwarding or inbound reception. The existing dispatcher and final recording admission label their distinct preflight phases. Reports contain only the stage, an allowlisted reason and a valid HTTP error status when available. They exclude provider messages, URLs, phones, account IDs, caller IDs, credentials and response payloads. Successful checks stay quiet. Logging failure cannot alter the original admission result.

Each attempt still makes the same four independent provider GETs with the original deadlines and exact identity checks. Missing metadata, failed reads, queued or changed forwarding, revoked caller ID and invalid ingress still hold the call. No extra read, retry, fallback number, recording creation, queue mutation, financial admission, provider configuration or customer-visible wording is added. The one-use configuration recovery stays unchanged.

Offline verification covers positive and negative readiness, four-stage transport/HTTP/malformed/response-type failures, timeout classification, private-data exclusion, hostile diagnostic fields and logger failure. The real dispatcher fixture verifies no reserve or dial after a readiness hold. The real recording service with local provider adapters verifies the final boundary records the failed stage before any recording admission. Existing recording, pre-dial abort and owner-readiness tests remain required with TypeScript and canonical release checks.

A separate bounded account diagnostic found three incomplete opportunity buffers (1/25, 15/25 and 7/25), so none qualified for the existing full-buffer overnight wait exemption. At that observation all three were blocked from new acquisition by the shared request pacing policy. Provider availability was true; the minute and daily request totals were below their hard limits, but only one or two ordinary paced tokens were available. The existing scheduler protects the next third token so fresh exports are not starved by two-request continuations. This is a capacity observation, not proof of a scheduler defect or authorization to consume protected reserves, increase quotas, replay old work or clear workflow flags.

Release this diagnostic code through the normal exact-commit checks. Only new ordinary production evidence can identify which readiness check fails next; the historical cause remains unknown. No account recovery or delivery claim follows from this change alone.
