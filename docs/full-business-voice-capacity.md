# Full Business voice capacity

The November 17 request to increase dialer capacity supersedes the earlier 80% application ceiling. The existing verified Business subscription supports forty simultaneous agent conversations. This release uses **38 outgoing slots plus two incoming slots**. The outgoing agent's existing daily limit remains 1,000; incoming settings, subscription, billing, overages, burst mode, prompts, tools, recording policy and all customer/contact admission remain unchanged.

This is available capacity, not completed calls. At the read-only morning inspection the previous 30-outgoing pool had one held operation and 29 free slots. No eligible due targets were inside their calling window before 9 AM Central. More configured slots cannot by itself cure unavailable contacts, hours, unknown receipts or a busy database selector. The existing one-second call issuance, asynchronous call handlers and per-account one-to-three-call allowance remain authoritative.

## Install and release

1. Independently review the byte-identical `config/full-business-voice-capacity.sql` and generated migration. It source/ACL-pins the five observed capacity functions, changes only three application ceiling expressions from 32 to 40, preserves their owner and security metadata, and adds a separate disabled one-use change policy. No observed capacity, original receipt, account balance, waiting job or provider setting changes during installation. Apply the migration and schema history together using the existing release runner transaction. A source or ACL mismatch aborts the complete transaction; never replace the expected hashes just to continue.
2. Run focused provider, SQL and native concurrent claim tests and the ordinary exact-head Reliability checks. Merge through the existing automatic release controller. Verify the exact canonical main SHA on both Vercel and Railway, healthy worker heartbeat, installed migration source/ACLs and the prior applied 80% receipt. Do not enable while either service is still on older code.
3. Once those concrete checks pass, an operator invokes the service-only `icash_full_business_voice_capacity_change('enable', '<verified-main-sha>')`. The first release binding is permanent. A different SHA, a reset or a completion without the original claim cannot authorize provider work. Normal authenticated production maintenance calls the new adapter; do not invoke a paid development call to verify it.
4. Maintenance validates its canonical production repository/main environment and exact activation SHA, fresh subscription metadata proving the paid forty-call plan and available credits, the saved reviewed outgoing agent/branch/version/configuration, existing 30/1,000 limits, disabled burst/queue settings and matching main-branch call limits. Only a winning database claim with the original and expected complete configuration hashes permits one minimal provider PATCH from 30 to 38. It rereads the reviewed branch and requires the exact expected hash before recording applied completion.
5. Verify the applied receipt, immutable before/after hashes and ordinary fresh observations of forty total, thirty-eight outgoing and two incoming. Only an applied/verified adapter result allows ordinary observation to use the forty-slot ceiling; disabled, held or failed verification retains the earlier 32 cap. Lower provider subscriptions and lower observed agent settings always win. Verify ordinary production dispatch receipts separately from configured capacity; no guaranteed throughput is implied.

## Uncertain outcomes and rollback

A lost PATCH response never authorizes another PATCH. The claimed operation may complete only when a GET of the exact reviewed branch matches its saved original expected hash. A new independent review fingerprint or an externally changed 38-slot setting cannot fabricate completion. Unknown or changed outcomes remain held. Repeated claims, routine provider observations and later manual reductions cannot clear the one-use claim or historical Pro/80% receipts.

The old 80% adapter reads its already-applied receipt before checking provider settings, so the newer 38-slot state cannot invalidate it. After full activation the applied status remains readable by later compatible releases, while a pending claim/complete remains bound to its exact approved release. During a rollback, retain code that recognizes the separately approved 38-slot fingerprint; do not run an older incompatible caller against the changed agent. A deliberate provider reduction needs its own reviewed operation and must not reset this receipt.
