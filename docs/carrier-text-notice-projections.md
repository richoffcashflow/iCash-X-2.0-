# Carrier notice response projections

Install `20261108235000_carrier_text_notice_projections.sql` only after the shared classifier/final-guard foundation migration. This change uses the foundation's whole-message, attachment-aware predicate rather than a second phrase-matching policy.

- Reply summaries, unread counts, latest-contact selection and workspace response ordering filter source rows before ranking or pagination. Raw text history remains available with neutral “Automated notice” attribution.
- Historical opportunity caches are repaired immediately for exact account/property rows containing a confirmed notice. Only `responded` and `response_at` change. Genuine human text, call and email responses remain evidence; attachment captions, quotes, mixed prose and unknown messages remain unchanged.
- The migration bounds its affected set to 10,000 properties and aborts above that bound. It acquires the existing account refresh advisory locks in account order, aborting rather than overwriting an in-progress refresh. Only affected refresh cursors are invalidated, and existing workspace revisions are incremented.
- Original message/event bodies, outgoing delivery states, cost records, suppression, manual controls, consent and immutable experiment/promotion history are not rewritten. Removing a false response is not permission for another outreach attempt; transport and dispatch checks continue using preserved original evidence.
- Assistant and voice context use filtered source rows before their history limits, with defensive shared classification at the application boundary. Human quotes and attachment captions remain conversation evidence. Saved raw history is not deleted.
- Attention and completed-reminder deployment checks use the service-only response views with the existing account/property/receipt predicates. PostgREST must expose the views' inherited relationships before releasing application queries. The existing readback gate exercises the seller-gap direct and nested shapes without reading message content.

## Offline verification

`carrier-text-notice-projections.test.mjs` executes the scoped current SQL predecessors and the real patch in isolated PostgreSQL (PGlite). It covers stale cached responses, account binding, count/pagination order, late-human ordered replay, genuine voice/email/attachment evidence, raw messages/costs and unchanged service-only function privileges. `carrier-text-notice-rendering.test.mjs` renders the actual conversation component and verifies neutral notice attribution without losing text, human quotes, attachments or outgoing authors.

The context, conversation inbox, workspace activity, archived attention and attention-readback suites cover the connected callers. These tests make no live provider calls. `scripts/test-carrier-notice-projections-postgres.py` also runs actual overlapping transactions in a disposable native PostgreSQL cluster, bound only to loopback. It verifies a busy newer refresh aborts the migration without overwriting its result/cursor/revision, and a human committing while the repair holds its lock is preserved. A controlled insert after the repair's source snapshot is immediately reflected in reply/count queries; the invalidated cursor corrects the derived cache at the next refresh. Raw notices and human messages both remain intact. Run it with psycopg3 and `ICASH_TEST_PG_BIN_DIR` pointing to an existing official PostgreSQL installation. It never accepts a production database URL.

Deployed PostgREST relationship discovery still requires release verification. No production migration is part of these tests.

## Remaining history and attention readers

The follow-up `20261108235100_carrier_text_notice_history.sql` filters the four retained receipt-bound reception readers before their twelve-message history/name limits. Their nonce, account/contact, permission, suppression and raw outgoing-invitation checks are unchanged. The current `contact_first_name` helper does not read SMS history and is unchanged.

Historical unbound route reviews and exact notice-derived text handoffs use separate service-only, security-invoker views. Route `needs_review`, revision, source records and unresolved control state remain untouched. A handoff is hidden only with the canonical account/property/party/source link and matching original quote and summary; an older genuine summary or unknown/mismatched source remains visible. The assistant existence query, workspace lists and property attention joins use these views before limits. Priority and notification source readers use the same filtered sources, including the retained `icash_attention_sources_before_journey` reader. Notification consent, claim/final authorization, source versions, existing provider receipts and non-text channels are unchanged.

Before application release, verify authenticated service-only zero-row PostgREST reads of `icash_response_sms_route_reviews` and `icash_response_handoffs`, plus the handoff's inherited `active_property:icash_screening_jobs!inner()` relation and `icash_handoffs:icash_response_handoffs!inner()` property embed. Use contradictory ID predicates; do not log source bodies. The earlier message/attention/SMS-request/seller-gap view relationship prerequisites still apply.

`tests/carrier-text-notice-history.test.mjs` executes the exact retained SQL functions with synthetic receipts, a full page of notices, human self-introduction and an attachment caption. It verifies source-bound route pagination, preserved route holds, linked versus older handoffs, real signature-task priority and unchanged notification source versions/privileges. The native PostgreSQL harness additionally proves actual anonymous/authenticated query rejection and service-only invoker access for both new views.
