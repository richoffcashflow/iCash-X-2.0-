# Property-aware calling and matching seller texts

Local review candidate only. No provider configuration, production SQL, outbound call or text was changed by preparing this patch.

## Behavior

- Outbound seller call: use the permission's exact account and screening snapshot, identify the saved AI assistant/business, and ask whether this is the owner of the specific address. Wait for that answer before asking about selling for all cash. A yes to ownership is not a yes to selling.
- Returning seller: greet the first name only when the exact contact's real recent message history contains a self-introduction after an actual outgoing message. Use the bound recent SMS and up to three completed, same-account/property/contact outbound-call transcripts to avoid repeating already answered qualification. Only an exact property-owner question followed by an unambiguous affirmative skips renewed ownership qualification; wrong-property or ownership corrections cancel that shortcut. A property-record owner name is not proof of who answered.
- Preserve private reviewed negotiation ceiling and existing server authority checks. Do not put the ceiling in the public dynamic variable or greeting, and explicitly prohibit disclosure of internal limits or margins. Buyer calls preserve their approved opportunity/asking-price path.
- Business inbound: context comes from the exact admitted CallSID, conversation, binding hash and hashed capability. Unknown context stays generic. Existing admission still refuses ambiguous tenant bindings before spending; it is not relaxed by this change.
- Active reception: an explicitly reviewed policy opt-in uses the admitted receipt's fixed called-number account and exact contact/deal joins. Unique seller binding gets an address-confirmation opening and, where grounded, the self-introduced first name. Multiple/unknown matches ask the caller to supply the address and never enumerate candidates.
- Inbound caller ID is a routing hint, not authentication. No private conversation bodies, owner-record identities, approved deal numbers or internal limits are exposed by these context RPCs. Claimed ownership does not unlock them. Authenticated private-history continuation requires a separate verification design; it is not silently inferred here.

## Installation and separate activation

1. Apply `config/call-property-context.sql` and `config/reception-property-context.sql` after their prerequisites, and `config/sms-seller-opening.sql` after the existing campaign/integrity migrations. These are local additive review candidates. Inspect exact prerequisites in each header.
2. Deploy the application changes. Legacy `message_only` reception remains unchanged. Owner quick-test restrictions, approved caps, reservation, receipt matching, account pauses and global release gates remain in force.
3. For property-aware reception, obtain an explicit policy/configuration review. BLOCKER FOR AN ALREADY-USED LANE: `icash_reception_private.guard_config` makes every field except `enabled` immutable once any receipt exists. This candidate intentionally preserves that guard. A separately reviewed renewal/upgrade mechanism must first preserve all prior receipts/settlement bindings, require the lane disabled and zero outstanding reservations, and audit the exact old/new approval. Do not disable the trigger, delete receipts, or rewrite prior financial approval to bypass it. Through that authorized renewal mechanism (or a genuinely unused configuration), set `context_policy` to `property_intake_v1`, the exact `propertyReceptionPolicyHash` exported from `lib/reception-property-context.ts` (current candidate: `44fe91fa860afe2a83d897ffa647c2d42661fb2cdcdc0c0630da24218ee79e60`), and a concrete `context_approval_reference` using the trusted database-owner process. No service-role policy-write RPC is introduced.
4. While the lane is disabled for the reviewed update, regenerate the dedicated branch body with `receptionBranchBody`. The exact greeting is `{{icash_property_greeting}}`; the prompt is `propertyReceptionPrompt` and consumes only `{{icash_property_context}}`. Voice/model/privacy/tool settings and owner-test caps are retained by the existing builder. Do not enable arbitrary prompt/first-message overrides on this reception branch.
5. The existing setup flow must be compatible with that renewal before it can save the changed fingerprint on an already-used lane. Publish only after separate authorization, read the actual branch/version back, and use `inspectReceptionAgent` to compute and verify its complete provider configuration fingerprint. Save that exact version/fingerprint through the existing reviewed setup flow. A source prompt hash alone is not a provider fingerprint and cannot be substituted.
6. Re-enable only the separately approved profile. The code does not broaden the current owner-only test to general callers. Test the owner-approved scenario once within its approved cap, and reconcile the actual receipt and costs; do not automatically redial or resend on an uncertain result.
7. Outbound seller configuration must permit the reviewed first-message and prompt overrides. Missing permission holds before reserving credits or placing a call with `property_context_override_review_required`; it is not modified automatically.
