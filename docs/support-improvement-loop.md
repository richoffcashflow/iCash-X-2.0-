# Continuous support improvement

The owner requested a support system that keeps improving without repeated manual audits on November 8, 2026. The loop connects observed conversations, verified product facts, regression tests, the existing automatic release controller and post-release evidence. It improves answer logic and fixes verified software defects; it does not automatically retrain a model on raw customer messages.

## Immediate response protection

Existing deterministic product guidance, model-response checks, account evidence and atomic reply finishing remain in place. Two failed troubleshooting follow-ups in the same issue now trigger management review instead of another cycle of instructions. A single failed step, an unrelated question, routine product guidance, an intervening operator response or a successful result does not create that sequence. Guest and account chat use the same detector. The server records management review together with the actual saved reply; the model cannot claim a handoff independently.

## Durable evidence and boundaries

The private checkpoint holds schema version, last completed watermark, backlog cursors, bounded processed evidence keys, pending/uncertain actions, pattern decisions, linked tests/PRs, verified deployment times, and comparable pre/post observations. Retain unresolved patterns until verified closed; trim processed deduplication keys only after their overlap/review window expires. Keep at most 1,000 recent keys and 100 active pattern records per checkpoint; if a bound is reached, retain continuation state and report limited coverage. Replace the same Library identity; do not create a new state file every run. Store no passwords, credentials, raw transcripts or card details there. Losing the checkpoint triggers read-only reconstruction from current releases and open work before further mutations.

No retrospective customer messages, refunds, new charges, subscription/access/identity changes, unpausing accounts, new outreach, paid model experiments, provider purchases, billing-policy rewrites or permission changes are authorized by this loop. Those need their existing verified workflows or the owner's concrete authorization. A support-copy fix does not repair the underlying account problem. Case triage, when actually necessary, must use current status/timestamp/latest-message guards and read-back; never mark an issue fixed from a heuristic or close it to improve a metric.

## What is measured

`SupportQualityReport.improvement` adds bounded, private candidates and stable pattern groups to the existing operator-only, no-store endpoint. It records customer-reported successful outcomes, closed cases lacking explicit confirmation, repeated failed steps, unanswered turns older than 15 minutes, unresolved payment/access concerns, dispute language and operator corrections. The admin panel shows sample counts. The offline CLI emits no raw transcript text.

Closing a chat, a thank-you, a passing test, a healthy service or a verified deployment is not customer-confirmed resolution. A correction supplied by an operator still needs product/evidence validation before it becomes shared guidance. Partial samples cannot establish total coverage, a resolution rate or a dispute rate. Actual chargeback trends require separately verified payment/dispute records and a consistent transaction denominator; do not infer them from threatening language. The objective is fewer recurring failures, fewer unresolved paid-access cases and useful progress for the customer, not fewer escalations or artificially closed chats.

Unconfirmed payment/access and dispute signals retain their review priority after a case is closed or marked resolved. The actual workflow status and active-case count remain unchanged. This preserves review evidence; it does not reopen cases, send messages or establish a verified account fault. Explicit customer confirmation and the existing operator/topic boundaries still apply.
